## 聊天分工与路线验收

1. **本聊天作总交接。** 管理版本、场地、待决问题、回退和验收结果。建议从本聊天分出上位实现聊天，开场限定“只读核对上位代码，先出图；下位只读”。下位核对时独立对着所选固件代码作答。工作较大时可另开独立评审聊天，先给它需求、图、SHA 和改动，不先给实现方的结论。分出的聊天不等于 Git 分支；不同聊天不同时写同一目录或同一交接文件。
2. **出图优先。** 凡会改变选物、车位、路径、朝向、速度、判障、时序、退出条件的修改，先在同一张实际场地图叠加改前/改后（旧实线、新虚线，带箭头和编号）。注明单位、原点、红蓝镜像、起终点、预备点/容差、固定障碍、夹爪和载荷扫过的面积；展示正常路线及本次涉及的卡住/退让/返程。若路径形状不变，标出哪段动作、速度或等待变化。没有轨迹日志就标“代码推算”，不能说成实跑。现有 [门前局部示意](gate.svg) 不替代整个场地图；简模导出后补上实测轮缘/爪尖、定位参考点、朝向和误差。
3. **每个编号只回答队员关心的事：** “以前在这里做什么 → 以后做什么 → 为什么 → 没成功怎么办”。上位说明会发哪条命令、等什么回包；下位从自己的代码独立说明实际动作、重复/取消/未完成如何回报。分歧保留，先问人，不靠伪造完成、省略审核或静默改阈值调和。
4. **确认后再实施。** 建议与已批准、改过与验证过分开列。实现后更新同一张图，验证改动路径、边界与失败出口，保存两端 SHA、配对测试、未覆盖项、固件哈希和回退方法。有条件再叠实跑轨迹/视频。继续沿用现有审核与授权规则；未经明确指示不改备份、不更新模型、不烧录。
