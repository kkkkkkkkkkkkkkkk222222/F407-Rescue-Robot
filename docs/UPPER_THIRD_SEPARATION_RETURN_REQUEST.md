# 可直接发给上位机Codex：第三次分离复审非法，张爪退让后返中

请配套F407基于cf99001的本次修改。已新增状态mode47，未新增UART命令、字段或帧类型。
原0x1D→0x18和0x1E→0x17配对上下文、READY/VALID及真实视觉帧编号继续使用。

## 一、严格限定改动范围

**只修改“第三次分离后，已完成复审且仍非法”这条失败路径。不要把所有失败、所有mode24都改成返中。**

- 第二次相对第一次夹持基准向张开方向松10°；第三次相对第一次松20°，不是累计松30°。
- 每次物理分离完成后，必须使用新真实画面重新累计三帧审核。
- 第三次READY=0时不能提前判失败；第三次READY=1、VALID=1则仍正常GRAB/运输。
- 第三次READY=1、VALID=0才走新的失败返中流程。F407会本地检测并执行；可能直接看到mode24/47，不应坚持先看到一次READY非法回报才承认恢复。
- 前两次失败、没有合格物资、无法确定方案、观察超时等原有放弃路径仍按其既有逻辑执行；非第三次已确认非法的退出仍可张爪→退300 mm→转90°→mode3。
- 原聚集360°恢复、开局藏堆、扫障mode46失败返中及正式投送mode16抬爪退出，不要改成此流程。

## 二、下位机现在的动作与状态

第三次复审非法：

1. 进入mode24，锁存本轮目标已取消，停止靠近，清旧审核/跟踪。
2. **先双爪完全张开，等待张爪动作完成。**不是后退后再张爪，也不重新夹紧。
3. 保持张爪，沿当前航向后退300 mm；重复HOLD不重置里程原点。
4. 后退完成停车，进入新增mode47：`TASK_CAPTURE_RETURN_WAIT`。
5. mode47表示爪子已开、300 mm退让已完成、正在等待上位机RETURN_CENTER。此处不转90°、不直接SEARCH。
6. 收到归属合法且参数有效的RETURN_CENTER后，F407进入mode17，继续用T265计算的实时H/D返中心。
7. 中心D=0后进入mode3，才允许下一轮目标。

mode47与扫障mode46不同：47是普通第三次分离失败；46仍是原物资找回失败。不得把它们的物理前置动作混用。
mode47没有自动等待超时，不发FAULT/ABORT；RETURN未到达时保持停车。RETURN返中途中通信过期按既有500 ms规则停车保留阶段，新有效H/D到达后恢复。
提前在mode24发RETURN不会打断张爪/后退，该状态不接受此返中请求；请等新鲜mode47再发送。
原有PAUSE/ABORT、边界恢复及硬件/位姿故障仍有优先级，不可把FAULT当作“已完成300 mm退让”。

## 三、上位机状态机建议

新增常量：`STM_MODE_CAPTURE_RETURN_WAIT = 47`。
在所有相关状态白名单、expected_stm_modes、状态展示/日志解析中识别47，不把它当未知状态。

建议使用独立恢复分支：

`第三次分离复审非法/观察到恢复 → 等mode24退让 → 看到47 → RETURN_CENTER → mode17 → 中心mode3 → 新画面新任务`

具体要求：

1. mode24期间持续发送HOLD，使用**下位机当前已接受的task_id/action_id**，不要重发旧APP、GRAB、第四次分离或TASK_COMPLETE。
2. 不能仅凭mode24推断需要返中：普通聚集恢复/其它放弃可能直接回3。只有新鲜47才确定启动本条返中路径；若直接收到3，就按原有搜索恢复处理。
3. 看到47后清除旧selected_batch、track、聚集框、夹内审核和待发分离请求，清除携带物清单（爪子已开）；**保留任务进度标志**。
4. 复用原RETURN_CENTER实时H/D生成函数，目标为既有场地中心，不在F407新增中心坐标。
5. RETURN沿用当前已接受task_id，分配按16位规则更新的action_id。每次H/D更新或重发保持同一action_id；非视觉RETURN的vision_frame=0。持续发布帧对，不能只发一次。
6. 返中阶段要求task/action上下文匹配，再结合新鲜mode17/3判断。不要把ACK或action_status bit0当作已回中心。
7. 收到对应返中动作的新鲜mode3后，建立新的视觉frame floor，重新扫描选择目标，分配新的task_id。旧APP不能复活已取消任务。
8. 同一轮最多三次物理分离；目前b0f954f默认disperse_limit=2，需要改为3并复核相关重试分支。第三次仍非法不允许通过换保留侧请求第四次绕过放弃决策。

## 四、必须处理context_pending等待门

b0f954f的 `_output_for_cycle` 在上下文不匹配时会持续重发protocol_last_output，可能挡住mode24/47恢复。
请在此等待门之前处理新鲜的24、47、3（及现有41/46）等恢复证据：

- 取消已过时的pending请求，不再重发被拒绝的第四次分离/GRAB。
- 用状态回执中的已接受task/action发HOLD，再在47转成新action的RETURN。
- 不要求F407把被拒绝的旧请求写成“已接受”。
- 摄像头恢复或显式暂停时，PAUSE也要发送到已接受上下文，而不是尚未被接受的动作编号。

## 五、禁止改变的任务语义

- 这是失败放弃，不是一次正式投送完成。
- 不发送或要求TASK_COMPLETE，不增加投送次数。
- 不修改first_common_delivered/first_delivery_done、initial_stash_done或进攻/防守选择。
- 首件未完成时，返中后仍只允许恰好1件GREEN；后续普通/核心合计最多2件，伤员单件。
- 保留20°观察、300 mm限推、开局速度、对正容差、S1投送退出升降、650 mm/1500 ms推送及1秒投送观察策略。

## 六、部署与验证边界

F407本次Debug编译通过；未新增/运行回归测试或烧录，未实车验证。
上位机必须先识别mode47并补好RETURN交接；旧上位机不识别47时，下位机会安全停住等待，不会自行跳SEARCH。
